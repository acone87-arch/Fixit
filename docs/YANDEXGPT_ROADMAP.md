# YandexGPT в Fixit — план внедрения

Дата создания: **19.10.2026**. Статус: **AI-00 в работе: набор и инструменты готовы, доступ к обеим моделям проверен реальными вызовами; baseline и выбор модели впереди**.
Исходный локальный commit при подготовке: `a77b363`. Это ориентир изученной структуры, а не подтверждение состояния production.

Этот файл — основной план AI-направления. По мере работы обновлять статусы и журнал здесь, сохраняя решения и доказательства. Общий [roadmap пилотной готовности](PILOT_HARDENING_ROADMAP.md) остаётся журналом существующего продукта; AI не переоткрывает завершённые P0 и не закрывает остаточные parity-задачи.

## 1. Цель и ожидаемый результат

Помочь техникам быстрее оформлять ремонт, диспетчерам — разбирать обращения, руководителям — видеть причины повторных выездов. Все функции работают внутри текущего Fixit Pulse, заявок и паспортов оборудования.

Первая версия содержит две возможности:

1. **«Оформить результат»** — из короткой заметки получить редактируемые поля диагностики, работ и комментария.
2. **«Что важно знать»** — получить краткую историю оборудования перед выездом со ссылками на исходные записи.

Пользователь проверяет предложение и сам принимает его. Сохранение ремонта, согласования, списание деталей, статусы и PDF продолжают проходить через существующие механизмы Fixit. Недоступность AI не мешает выполнять работу и синхронизировать её.

Конечная цель направления: после успешного пилота последовательно добавить разбор заявок, клиентские объяснения, помощника по инструкциям и управленческие сводки. Каждый следующий этап выпускается при подтверждённой пользе предыдущего.

## 2. На что опираемся в проекте

Изучены структура и конкретные точки интеграции; runtime-аудит в рамках подготовки плана не проводился.

| Область | Текущая реализация | Следствие для AI |
|---|---|---|
| Backend | FastAPI, async SQLAlchemy, PostgreSQL; `app/main.py`, `app/config.py` | Вызовы провайдера выполнять сервером через отдельный сервис |
| Авторизация | `CurrentUser` в `app/core/deps.py`; организация определяется сервером | Не принимать tenant из AI-ответа или доверенного на словах клиентского параметра |
| Права на данные | `app/services/access_policy.py`, клиентский scope и TechnicianClientAccess | Проверять заявку, оборудование и каждую включённую историческую запись |
| Единая работа | `ServiceRequest`, `Repair.service_request_id` | Строить новые сценарии вокруг канонической заявки; Task/Ticket учитывать только как историю |
| Рабочая форма | `app/static/app.js`: `draft.diagnostic`, `draft.work`, `draft.comment`, `RequestDraftStore` | AI заполняет существующие поля через предварительный просмотр |

| Паспорт | `app/routers/equipment.py`, `GET /equipment/{id}/passport` | Переиспользовать правила отбора истории, выделив общий сервис при необходимости |
| Акт | `app/services/service_act_pdf.py` | В PDF попадает только подтверждённый результат ремонта |
| Склад | `app/services/stock_service.py` | Модель не изменяет остатки и не создаёт движения |
| Проверки и выпуск | `tests/`, `.github/workflows/pilot-onboarding.yml`, `.github/workflows/deploy.yml`, production runbook | Добавить AI-проверки в действующие процессы, не создавать обходной выпуск |

## 3. Правила реализации

- Превращать только сообщённые факты в аккуратный текст. Не дописывать измерения, причины поломки, замену деталей, успешную проверку, трудозатраты или подпись клиента.
- Разделять установленный факт и предположение. Если данных недостаточно, вернуть вопрос или сообщение о недостатке данных.
- Генерация не записывает бизнес-данные. Применение текста в форму и последующее сохранение — отдельные явные действия пользователя.
- Права на чтение недостаточны для редактирования: возможность применить результат соответствует текущим правам и состоянию рабочей формы.
- Выдавать модели минимальный контекст. Телефоны, email, подписи, токены, ссылки доступа и прочие ненужные данные исключать до обращения к API.
- Текст заявок, истории и документов считать данными, включая содержащиеся в них инструкции для модели. Они не могут менять системные правила и права.
- Использовать отдельные флаги функций, разрешение для организации, ограничения расхода и общее быстрое отключение AI.
- Модель и версию промпта фиксировать для каждого запуска. При доступности закреплять версию модели; обновления проверять на эталонном наборе до выпуска.
- Не начинать с дообучения, общего чата и автономного агента. Сначала проверить качество на ограниченных сценариях.

## 7. AI-02 — «Оформить результат»

Предлагаемый контракт: `POST /api/ai/service-requests/{id}/repair-draft`.
Вход: `operation_id`, заметка или текущие поля формы, ревизия локального черновика. Связи и текущие права сервер получает самостоятельно. Выбранные детали можно передавать только как отдельные подтверждённые пользователем данные с проверкой принадлежности организации.

Выход: `generation_id`, `diagnostic`, `work`, `comment`, `questions[]`, `warnings[]`, версия схемы и ревизия входного черновика. Утверждённой схемы ремонта этот ответ не заменяет.

- [ ] AI-02.1 Подготовить промпт с примерами, запретом домыслов и сохранением отрицаний. Нечёткое «поменял уплотнение» не превращать в конкретный артикул; «планирую заменить» не превращать в выполненную работу.
- [x] AI-02.2 Добавить в рабочую зону Pulse ввод заметки/использование заполненных полей и кнопку «Оформить результат». Включать по тем же состояниям и правам, что и редактирование ремонта.
- [x] AI-02.3 Показать исходный текст и предлагаемые поля, вопросы отдельно; действия «Применить в форму» и «Отмена». Применение не закрывает заявку.
- [x] AI-02.4 Защитить от позднего ответа: при изменении формы, смене заявки или повторном запуске старый ответ не перезаписывает свежий ввод. Подтверждённые изменения сохранять через существующий `RequestDraftStore`.
- [x] AI-02.5 Сохранить текущую сборку `fault_type`/`description`, `local_uuid`, `parts_used`, отправку фото, сервисный акт и durable sync. AI не создаёт ремонт сам и не редактирует уже подписанный акт.
- [x] AI-02.6 В офлайне показывать причину недоступности генерации. Принятый ранее текст остаётся в локальном черновике и отправляется обычной очередью. Саму генерацию не ставить в Background Sync.
- [x] AI-02.7 Записывать применение/отказ/оценку пользователя. Feedback не является доказательством фактического сохранения: для сохранения связывать `generation_id` с каноническим ремонтом через совместимое необязательное поле, либо отдельное подтверждённое сервером событие после sync. Не менять смысл `local_uuid`.

**Приёмка:** минимум 95% ответов контрольного набора сохраняют все явно сообщённые ключевые факты; ни одного добавленного факта о замене, проверке, замерах, времени или подписи. На 100% критических примеров корректно сохранены отрицания и различие «сделано/планируется». В браузере подтверждены отмена, повтор, поздний ответ, перезапуск, офлайн-сохранение и дальнейший sync. AI-ошибка не теряет исходную заметку.

## 8. AI-03 — «Что важно знать»

Предлагаемый контракт: `POST /api/ai/equipment/{id}/brief`. Endpoint авторизованный; выдача по оборудованию не расширяет доступ к отдельным ремонтам.

Выход: краткое резюме, пункты `facts[]` с `source_ids[]`, явно помеченные наблюдения, `coverage` (интервал, число доступных/включённых записей, усечение), `generated_at`, `context_hash`. Ссылки строит Fixit из проверенных ID, а не модель.

- [x] AI-03.1 Выделить выборку истории с существующими правилами ACL. Legacy-записи помечать и исключать дубли канонических событий; недоступные поля/комментарии не включать.
- [ ] AI-03.2 Ввести предел записей и токенов; сначала использовать последние релевантные ремонты. Показать границы выборки; не писать «за всю историю», если история усечена.
- [x] AI-03.3 Для каждого фактического пункта требовать ссылку на переданный источник. Неизвестные ID отклонять. Семантическое соответствие факта источнику оценивать отдельно: валидный ID сам по себе не доказывает верность текста.
- [x] AI-03.4 При пустой истории показывать «Истории пока недостаточно». При противоречиях сохранять обе версии с датами и источниками, не выбирать выдуманный итог.
- [ ] AI-03.5 Добавить блок в заявку/паспорт. Проверить открытие источников с теми же ACL. При изменении истории помечать сводку устаревшей; обновлять по явному действию.
- [ ] AI-03.6 Ключ повторного использования включает tenant, сценарий, доступный пользователю набор источников, их версии/содержимое, модель и промпт. Кэш одной организации или широких прав не выдавать пользователю с более узкими правами.

**Приёмка:** 100% фактических пунктов имеют существующие доступные источники; минимум 95% фактических пунктов подтверждаются их содержимым на контрольном наборе; ноль утечек и критических выдуманных выводов. Проверены empty state, ограниченная выборка, legacy, обновление истории, отзыв доступа и конфликтующие записи.

## 9. AI-04 — пилот первой версии

- [ ] AI-04.1 Включить только пилотной организации и выбранным пользователям. Провести короткое обучение: черновик, проверка, ручной путь, источники.
- [ ] AI-04.2 Собрать минимум 30 реальных применений оформления и 20 сводок за ориентировочно 1–2 недели. Если объём не набран, продлить наблюдение; срок сам по себе не является приёмкой.
- [ ] AI-04.3 Проверить каждую пилотную выдачу на добавленные факты, пропуски, неверные источники и исправления. Собирать отзыв «полезно/не полезно» с причиной; сравнивать время с baseline AI-00.
- [ ] AI-04.4 Подготовить отчёт: выборка и ограничения, медиана времени, доля применения, критические/обычные ошибки, p50/p95 задержки, расход, цена принятого результата, ошибки API, влияние на offline/sync.
- [ ] AI-04.5 Принять и записать решение: расширять / исправлять и повторять / остановить сценарий. До решения AI-05–AI-09 остаются backlog.

Предлагаемые критерии go/no-go, подлежащие фиксации в AI-00 до пилота:

| Показатель | Цель первой версии |
|---|---|
| Медиана времени оформления сопоставимых ремонтов | Снижение минимум на 30%, включая проверку и исправления |
| Применение черновиков оформления | Не менее 70% валидных выданных черновиков; повторы учитывать отдельно |
| Полезность сводок | Не менее 80% оценённых сводок; также указать долю полученных оценок |
| Задержка | p95 ≤ 15 секунд для оформления и ≤ 20 секунд для сводки |
| Успешные технические ответы | ≥ 98% разрешённых запусков; учитывать timeout, невалидный JSON, отказы и 5xx |
| Критические ошибки | 0 утечек, 0 выдуманных выполненных действий, 0 изменений без подтверждения |
| Расход | В пределах `B` и согласованной цены успешной операции |
| Основная работа | Нет регрессий завершения ремонта, PDF, склада и offline sync |

Эти числа — целевые пороги, а не уже измеренные результаты. Любая утечка, самовольное изменение бизнес-данных или потеря черновика требует отключить затронутую функцию и устранить причину перед повторным включением. Повторяющиеся домыслы о выполненных работах также блокируют расширение независимо от средней оценки.

## 10. AI-05 — разбор входящих заявок

- [ ] Генерировать для диспетчера заголовок, краткое описание, предлагаемую категорию, обоснование и уточняющие вопросы из уже созданной ServiceRequest.
- [ ] Приоритет предлагать отдельно от фактов и не применять автоматически; критические признаки обрабатывать также детерминированными правилами продукта.
- [ ] Показывать возможные дубли с ID и причинами сходства внутри доступного scope. Не объединять и не закрывать заявки автоматически.
- [ ] Сохранить оригинальный текст и QR provenance. AI не должен задерживать публичный submit, менять его идемпотентность или блокировать получение обращения при недоступном API.
- [ ] До выпуска подготовить не менее 50 размеченных обращений, включая срочные и похожие обращения по разному оборудованию. Зафиксировать допустимые ошибки категорий и приоритетов; все критические примеры должны быть переданы диспетчеру без понижения важности.

**Приёмка:** диспетчер принимает/правит предложение явным действием; исходное обращение всегда доступно; проверены QR retry, scope, ошибка API и отсутствие автоматического merge. Польза измеряется временем разбора и количеством уточняющих контактов.

## 11. AI-06 — объяснения для клиента

- [ ] Готовить черновик объяснения по диагностике, выполненным работам и текущему согласованию.
- [ ] Создать отдельную выборку только разрешённых клиенту фактов. Внутренние обсуждения, себестоимость и сведения других клиентов исключать до передачи модели.
- [ ] Суммы, детали, сроки и статус брать из подтверждённых данных. При отсутствии срока не обещать дату; предложения не описывать как выполненные работы.
- [ ] Встроить просмотр и редактирование диспетчером. Публикация/отправка выполняется обычным явным действием; генерация ничего не отправляет.
- [ ] Проверить минимум 30 примеров, включая отказ в согласовании, ожидание деталей и незавершённый ремонт.

**Приёмка:** ноль утечек внутренних данных и неподтверждённых обещаний на контрольной выборке; связь каждого существенного утверждения с данными заявки; измеряются время подготовки и объём исправлений.

## 12. AI-07 — помощник по инструкциям и похожим ремонтам

- [ ] Собрать разрешённые к использованию инструкции с производителем, моделью, ревизией и датой. Назначить ответственного за актуальность документов.
- [ ] Организовать загрузку/извлечение текста, при необходимости отдельный OCR, разбиение на фрагменты, индексирование и версии. Выбрать поиск и хранилище по измерениям на реальном корпусе; не вводить векторную инфраструктуру заранее без проверки пользы.
- [ ] Разделить общие разрешённые инструкции и приватную историю организаций. Отбор по ACL выполнять до выдачи найденных фрагментов модели; удаление/отзыв документа инвалидирует индекс и кэш.
- [ ] Добавить ответ на вопрос в контексте конкретной модели оборудования с указанием документа, ревизии, страницы/раздела и фрагмента. Явно различать инструкцию производителя и исторический опыт ремонта.
- [ ] При отсутствии подходящего документа сообщать об этом. Не выдавать неподтверждённую универсальную процедуру как инструкцию для конкретного оборудования.
- [ ] Подготовить минимум 50 вопросов с эталонными источниками и 20 вопросов без ответа в корпусе. Включить разные ревизии модели, опасные действия и инструкции-инъекции внутри документов.

**Приёмка:** не менее 90% ответимых вопросов находят нужный источник в первых пяти результатах; не менее 95% существенных утверждений подтверждаются источниками; ноль опасных выдуманных процедур. Для вопросов без оснований помощник корректно отказывает либо просит уточнение. Допуск к эксплуатации подтверждает профильный специалист.

## 13. AI-08 — голосовой ввод

- [ ] Проверить на реальных телефонах техников и минимум 30 записях в характерном шуме; оценивать ошибки важных фактов, а не только общую точность слов.

**Приёмка:** пользователь контролирует запись и расшифровку; неподтверждённый текст не сохраняется в ремонт. Время с учётом исправлений лучше текстового baseline для выбранного сценария; критические ошибки распознавания явно проверяются человеком.

## 15. Общая проверка качества и безопасности

| Уровень | Обязательные сценарии | Доказательство |
|---|---|---|
| Контракты/адаптер | Успех, отказ модели, JSON error, неизвестные поля, усечённый ответ, timeout, 429/5xx, отмена | Тесты с fake provider, без платных вызовов в обычном CI |
| PostgreSQL/API | Tenant/client/site scope, read/write права, отзыв доступа, флаги, конкурентный бюджет, retry/идемпотентность, очистка | Реальные PG integration tests |
| Browser | Просмотр/отмена/применение, поздний ответ, смена заявки, перезапуск, доступность с телефона, HTML в AI-тексте | Chromium/Playwright и ручная проверка на устройстве |
| Offline | Сеть пропала до/после применения, сохранение черновика, повторный sync, старая очередь, совместимость payload | IndexedDB/SW runtime и существующие queue tests |
| Изоляция контекста | Поддельный ID, чужая история, клиентский кэш, инъекции, закрытый источник после отзыва доступа | API и eval cases с проверкой входа fake provider |
| Семантика | Домыслы, отрицания, источники, пустые данные, противоречия, большой контекст | Версионируемый контрольный набор и ручная экспертная оценка |
| Реальный провайдер | Доступная модель, схема, usage, задержка и стоимость | Отдельный ограниченный smoke/eval по явному запуску |
| Регрессии продукта | Завершение, PDF, склад, подписи, offline, клиентский scope | Действующие проверки, относящиеся к изменённому пути |

Перед релизом запускать обязательные gates текущего workflow. Не выдавать skipped/mock tests за проверку production или качества реальной модели. Для изменений миграций проверить upgrade с текущего head, чистый bootstrap и сохранение существующих данных. После смены модели, промпта, схемы или отбора источников повторять релевантную контрольную оценку.

## 16. Бюджет, наблюдаемость и эксплуатация

**Параметры пилота от 19.10.2026:** «Аквадез» и «Промтехсервис»; пользователь указал **300 ₽ в месяц**. Консервативная рабочая трактовка — единый общий лимит для обеих организаций, первичной оценки и повторов; месяц определяется по Asia/Yekaterinburg. В пределах этой суммы выбраны внутренние ограничения 10 ₽ в день и не более 30 ₽ на первоначальный сравнительный запуск. Это записанные параметры, их runtime-контроль пока не реализован.

Начальный сравнительный запуск — четыре одинаковых tune-примера для каждого кандидата, подробнее в [протоколе](../evals/yandexgpt/README.md). Маленькая выборка проверяет интеграцию и помогает отбору; критерии качества AI-02/AI-03 и объём реального пилота не снижаются. Полный дорогой eval выполнять только если его верхняя оценка помещается в остаток общего бюджета; иначе сокращать стоимость запроса без потери нужного контекста или переносить продолжение на следующий месяц.

Фактические цены брать из тарифа выбранной модели на дату подключения. Не фиксировать предположительную цену в рублях как обещание.

`Стоимость вызова = входные токены × тариф входа + выходные токены × тариф выхода` с приведением к единице тарифа. Отдельно учитывать распознавание речи, эмбеддинги, индекс/хранилище и повторные оплаченные вызовы.

`Цена принятого результата = все расходы сценария / число принятых результатов`.
`Экономический эффект = сэкономленные часы × согласованная стоимость часа − все расходы AI`.

- [ ] Завести метрики по сценарию и организации: вызовы, успехи/отказы, p50/p95, usage, резерв/расход, feedback, доля применения. Не использовать полный текст в labels.
- [ ] До достижения лимита выдавать предупреждение ответственному в согласованном канале; при исчерпании лимита прекращать новые платные вызовы. Уведомления подключать отдельно, не отправлять сообщения автоматически в рамках подготовки плана.
- [ ] Подготовить runbook: неверный ключ, исчерпанный бюджет/квота, недоступность API, плохое качество, утечка, зависший резерв, очистка данных, смена модели и отключение.
- [ ] Выпускать через обычный deploy с флагами OFF → staging → pilot allowlist → расширение после AI-04. Бизнес-транзакции не должны зависеть от AI API.
- [ ] Проверить откат: выключить флаг, остановить новые генерации, не применять поздние ответы, сохранить введённый/принятый текст и обычную очередь. Миграции при rollback не удалять вместе с данными; следовать production runbook.
- [ ] Для каждой организации перед расширением проверить разрешённые сценарии, данные, лимит и ответственного. Обновления модели сначала проходят контрольный набор и ограниченный пилот.

## 18. Как продолжать работу по этому плану

Для каждой задачи: сверить текущий код → подтвердить исходное поведение → реализовать ограниченный scope → выполнить подходящие проверки → записать результат, ограничения и следующий шаг здесь. Обновлять существующий план, не создавать дубли после каждого этапа.
