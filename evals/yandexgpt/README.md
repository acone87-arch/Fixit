## Содержимое

| Файл | Назначение |
|---|---|
| `repair_cases.jsonl` | 50 синтетических заметок; 35 tune / 15 holdout |
| `history_cases.jsonl` | 30 синтетических историй; 20 tune / 10 holdout |
| `baseline.template.json` | Пустой шаблон реальных замеров; нулевые измерения не подставляются |
| `pilot.template.json` | Параметры пилота и два кандидата, внешние вызовы выключены |
| `../../scripts/ai_preflight.py` | Проверка набора, экспорт входов, подготовка экспертной оценки и сводка замеров |
| `../../scripts/ai_cloud_check.py` | Явно запускаемая платная проверка синтетических примеров с локальным бюджетным журналом |
| `../../scripts/ai_semantics.py` | Сценарные промпты/схемы v2 и сборка текста из проверенных исходных свидетельств |

Все 80 примеров придуманы для проверки поведения. Это **не выгрузка ремонтов**, не репрезентативная статистика клиентов и не экспертно подтверждённый эталон. Во всех записях стоит `needs_domain_review`. Профильный техник/диспетчер должен проверить формулировки до приёмки качества. Затем набор дополнить обезличенными реальными примерами, не заменяя ими критические синтетические сценарии.

Проверки данных и unittest выполняются без сети, БД, ключей и сторонних Python-зависимостей. Утилита `ai_preflight` не импортирует приложение и `.env`. Отдельная `ai_cloud_check --run` читает только `.env.yandex.local` и делает платные вызовы; её результаты описаны в протоколе. Команды ниже запускаются из корня Fixit.

```sh
python3 scripts/ai_preflight.py validate
python3 -m unittest discover -s tests -p test_ai_preflight.py -v
```

## Состав набора и границы проверки

Заметки покрывают очистку, замену, ожидание деталей/согласования, отрицания, числа и единицы, неоднозначные описания, опечатки, невоспроизведённые жалобы, вредоносные инструкции и передачу работы. Истории — повторные обращения, нехватку данных, противоречия, legacy, ограниченную выборку и разные результаты ремонта. Оборудование без серийного номера допустимо.

Поля записи:

- `id`, `scenario`, `origin`, `family`, `split`, `tags`: идентификация и организация оценки.
- `input`: единственная полезная нагрузка для модели.
- `expected.required_facts`: факты/ограничения, которые оценщик должен найти в ответе; проверка семантическая, точное совпадение строк не требуется.
- `expected.forbidden_claims`: примеры недопустимых домыслов. Список не исчерпывающий: любое другое придуманное действие/измерение также является ошибкой.
- `expected.question_topics`: темы уточнений. Необязательные уточнения не должны выдавать предположение за факт.
- `expected.source_ids`: относящиеся к ожидаемому ответу источники. Для каждого фактического пункта нужен подтверждающий источник; допустим достаточный набор ссылок, искусственно цитировать все ID не требуется.
- `expected.acceptable_rendering`: одна допустимая формулировка для оценщика, не единственный правильный ответ и не полный JSON-ответ будущего API.

Источники истории имеют искусственные локальные ID. Даты, виды событий и тексты служат только фикстурами оценки. `coverage.truncated=true` требует явного ограничения выводов переданной выборкой. Наличие источника с корректным ID не доказывает истинность сделанного по нему вывода.

Разделение сделано по семействам: одинаковое семейство не пересекает tune и holdout. Валидатор проверяет эту границу, дубли ID/входов, минимальные объёмы и ссылки на источники, но не умеет подтверждать медицинскую/техническую истинность текста, обнаруживать все смысловые дубли или гарантировать отсутствие персональных данных в будущих дополнениях. Это проверяется человеком.

Holdout не использовать в примерах промпта или для его подбора. После первой оценки, на основании которой меняется промпт, использованные контрольные случаи считаются раскрытыми: до следующей независимой приёмки добавить новые. Файлы лежат в репозитории открыто для команды; это процедурное разделение, не секретное хранилище. При подготовке промптов читать только tune-экспорт.

## Как собрать baseline без AI

1. Скопировать шаблон в локальный каталог:

   ```sh
   mkdir -p evals/yandexgpt/local
   cp evals/yandexgpt/baseline.template.json evals/yandexgpt/local/baseline.json
   cp evals/yandexgpt/pilot.template.json evals/yandexgpt/local/pilot.json
   ```

   Каталог `local/` исключён из Git. Это защита от случайного коммита, а не механизм контроля доступа; реальные персональные данные и ключи туда не помещать.

2. Выбрать минимум 20 обычных ремонтов. Заранее отнести каждый к сложности: `simple` — одно понятное действие, `standard` — несколько действий в одной неисправности, `complex` — несколько проблем/незавершённая диагностика. Не менять сложность после просмотра времени. Собрать наблюдения более чем одного техника и отметить тип устройства/качество сети в отдельном локальном журнале.
3. Замерять только работу по оформлению и чтению истории, а не сам физический ремонт. Секундомером фиксировать непересекающиеся интервалы:
   - `text_seconds`: ввод текста;
   - `history_seconds`: поиск и чтение истории;
   - `network_seconds`: ожидание сети/загрузки, когда работа над формой остановлена;
   - `review_seconds`: чтение/проверка подготовленного текста;
   - `correction_seconds`: внесение исправлений.
4. Записывать действительный ноль, если действия не было. Неизвестное время нельзя заменять нулём; незавершённое наблюдение пока не включать в `sessions`.
5. Для каждого наблюдения добавить объект указанной ниже формы. Это **структура**, `null` здесь означает незаполненное значение; утилита отвергнет такую запись, пока измерения не внесены:

   ```json
   {
     "sample_id": "observation-001",
     "mode": "manual",
     "complexity": "standard",
     "text_seconds": null,
     "history_seconds": null,
     "network_seconds": null,
     "review_seconds": null,
     "correction_seconds": null
   }
   ```

   Идентификатор — локальный обезличенный код наблюдения, без ФИО/контактов и публичных ссылок на заявки. После подключения AI `mode=ai` измеряется так же, включая ожидание генерации в `network_seconds`, просмотр и правки. Не считать ожидание повторно как набор текста.

6. Получить сводку:

   ```sh
   python3 scripts/ai_preflight.py baseline-summary --input evals/yandexgpt/local/baseline.json
   ```

   До 20 ручных наблюдений выводится `insufficient_baseline`. После 20 — только `minimum_sample_collected`: это не доказательство репрезентативности, эффективности AI или разрешение выпуска. Сравнивать медианы внутри сложности и учитывать техника/устройство/сеть по локальному журналу. Не смешивать изменение сложности работ с эффектом AI.

## Проверка публичных возможностей провайдера

Проверено по официальным страницам 19.10.2026; доступ к двум моделям позже подтверждён запросами. Индивидуальные квоты и полный набор IAM-прав не аудированы.

| Вопрос | Публичный результат | Что требуется для нашего аккаунта |
|---|---|---|
| Кандидаты | Pro 5.1: `yandexgpt-5.1`; Pro 5: `yandexgpt-5-pro`; у обоих опубликован контекст 32 768 | Успешный вызов каждого URI подтверждён |
| Версии | Явные URI предпочтительнее алиасов `latest`/`rc`; вывод из эксплуатации требует смены URI и повторной оценки | Записать фактические model URI/version в результатах каждого запуска |
| Lite | В каталоге опубликовано отключение Lite 5 на 15.11.2026 | Не выбирать его основой нового внедрения без пересмотра жизненного цикла |
| JSON | Structured output предусмотрен для поддерживающих моделей; сочетание с `tools` запрещено | Smoke обоих кандидатов пройден через Completions API |
| Лимиты | Публичная квота синхронной генерации без подписки — 2 одновременных вызова | Проверить фактическую квоту; первый eval выполнять последовательно |

Источники: [каталог и жизненный цикл моделей](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models), [структурированный вывод](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/structured-output), [квоты](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/limits).

Для проверки выбран синхронный Completions API: одна генерация по явному контексту без постоянного диалога и файловых ресурсов. Endpoint и structured output проверены отдельным `ai_cloud_check`; `ai_preflight` остаётся полностью офлайн. Для серверного AI-01 предстоит реализовать асинхронный адаптер и общий PostgreSQL-учёт. Контракт: [пример структурированного запроса](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-structured).

### Обработка данных

Предлагаемая настройка адаптера — `x-data-logging-enabled: false` на каждом вызове. Она отключает использование содержимого запросов для улучшения сервиса, но **не отменяет** другие механизмы хранения. Трейсинг проверяется отдельно. При выборе Responses API необходимо отдельно рассмотреть `store=false`; сохранение диалогов для первых двух функций не требуется.

До реальных данных проверить настройки и записать подтверждение в локальный протокол. Предлагаемый разрешённый контекст: заметка, название/модель оборудования при необходимости, выбранные доступные события с датами и техническими текстами, границы выборки, локальные ID источников. В первой версии не отправлять ФИО, контакты, адреса клиентов, подписи, credentials, фото/аудио и URL доступа. Технический текст вручную очистить от встроенных персональных данных. Утверждение списка ещё не получено.

Источники: [отключение логирования](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/disable-logging), [разные категории хранения](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/security/data-storage). Прочтение документации не означает, что настройка в аккаунте уже выполнена.

### Стоимость и разрешение платных запусков

В шаблоне сохранён публичный снимок синхронных цен в рублях с НДС: Pro 5.1 — 0,80 ₽ за 1000 входящих и за 1000 исходящих токенов; Pro 5 — 1,20 ₽ соответственно. Скидки и кэш не предполагаются. Источник: [тарифы](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing). Перед вызовами проверить тариф именно аккаунта; снимок не является runtime-конфигурацией.

Иллюстрация, **не измеренный расход**: при 2000 входящих + 500 исходящих токенов один вызов обошёлся бы в 2 ₽ для Pro 5.1 или 3 ₽ для Pro 5. Один проход 80 случаев по двум кандидатам составил бы 400 ₽ при таком условном размере каждого вызова; реальные истории и промпты могут быть длиннее, повторы оплачиваются отдельно. Это не гарантированный предел и не утверждённый бюджет.

В `pilot.template.json` зафиксирован общий бюджет **300 ₽ на календарный месяц** по Asia/Yekaterinburg. Как внутренние ограничения в его пределах выбраны **10 ₽ в день** и **30 ₽ суммарно на первичную оценку**, включая smoke и повторы. Это не дополнительные суммы: тестовые и рабочие вызовы расходуют один общий бюджет. Не выдавать по 300 ₽ каждой организации. Коды `akvadez`/`promtekhservis` пока служат метками оценки, соответствие реальным tenant ID ещё не проверено.

Первичное сравнение уменьшено до одинаковых **четырёх tune-случаев на кандидата**: R001 (очистка), R011 (незавершённая работа), H001 (повторное обращение), H026 (нет проверки после замены). Восемь вызовов при условном размере выше стоили бы 20 ₽. Это только предварительный отбор и проверка API, не приёмка качества и не основание менять контрольные пороги. Отдельные smoke также входят в 30 ₽; не дублировать вызов, если он одновременно проверяет схему и даёт сравнимый результат. При дневном пределе испытание может потребовать нескольких дней.

Перед каждым реальным вызовом нужно резервировать верхнюю стоимость по действующему тарифу и лимитам токенов. Если остатка не хватает — не выполнять вызов, даже если средняя оценка кажется небольшой. Полный проход из условного примера за 400 ₽ превышает месячный бюджет и в таком виде не допускается. Расширять выборку по остатку бюджета и более точным измерениям; при недостатке средств продолжить в следующем месяце. Перед пилотом освободившиеся средства не считать основанием увеличить общий лимит.

Доступ и usage проверены, первичные вызовы ограничены локальным бюджетным журналом. Для дальнейшего расширения ещё нужны сверка тарифа с аккаунтом, подтверждение схемы обработки реальных данных и общий серверный контроль расходов. Предел цены успешной операции пока не выбран: подобрать по измерениям внутри указанных лимитов. Платный режим приложения остаётся `false`; диагностический CLI требует отдельного явного `--run`. Ключи в шаблонах и репозитории не хранить. Сам `pilot.template.json` ничего не включает, а изменение его полей не предоставляет приложению возможность платных вызовов.

## Протокол будущего сравнения двух моделей

1. Получить участников/бюджет и проверить аккаунт, модель/JSON smoke, logging и актуальный тариф. Выбрать одинаковые сценарные промпты/схемы, ограничения ответа и параметры для двух кандидатов; version/hash и параметры сохранить с результатами.
2. Зафиксировать контрольные суммы набора командой `validate`. Получить входы только нужного split:

   ```sh
   python3 scripts/ai_preflight.py export-inputs --split tune > evals/yandexgpt/local/tune-inputs.json
   python3 scripts/ai_preflight.py review-template --candidate pro-51 --split tune > evals/yandexgpt/local/pro-51-tune-review.json
   ```

   Экспорт содержит только ID, сценарий и `input`; критерии и примеры не отправляются модели. Файл `review-template` предназначен оценщику и содержит эталонные критерии — **его нельзя отправлять модели**. CLI ничего не отправляет самостоятельно.
3. На tune отладить промпты. Все запросы и технические ошибки учитывать, а не удалять неудачные случаи из знаменателя; повторы записывать как отдельные попытки. Текущий шаблон рассчитан на одну попытку на случай, для повторов нужен отдельный локальный журнал попыток.
4. Для каждой выдачи оценщик заполняет фактический ответ, `schema_valid`, сохранение всех обязательных фактов, критические домыслы, подтверждение источниками, задержку, usage и реальную стоимость. `null` — не проверено; для `sources_supported` в ремонтах допустимо оставить `null`, так как источников истории там нет. По одному случаю с несколькими фактами дополнительно считать подтверждённые/все фактические утверждения в локальном журнале, чтобы оценить порог AI-03.
5. После фиксации промптов выполнить holdout по той же процедуре, не подстраивая промпт по контрольным ответам. Таблицу сравнения составить отдельно по сценарию и split: число попыток/ошибок, сохранение фактов, критические ошибки, точность ссылок, p50/p95, usage и расход. При малой выборке p95 — ориентир, а не подтверждение production SLA.
6. Выбрать конфигурацию, только если она проходит критерии AI-02/AI-03; между прошедшими сравнить задержку и цену. Если не проходит ни одна — исправлять подход, а не объявлять победителя по средней стоимости. Записать выбор и ограничения в основной roadmap.
